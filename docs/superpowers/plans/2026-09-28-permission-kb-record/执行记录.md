## Rulings（preflight 阶段）

**Ruling A：T1 的回填测试范围要收窄。**
`test_platform_column_exists_with_backfill` 断言全表 `platform == {ANDROID}`——这在 T1 时成立，
但 T7 导入会加入 HARMONYOS/IOS 行，之后再跑全量回归这条测试必然失败（T1 Step 7 与 T7 Step 7 都会跑全套）。
改为断言「无 NULL/空 platform」+「已知旧行（`android.permission.CAMERA`）为 ANDROID」，
在 T7 之后仍成立且仍能证明回填正确。
*若判断有误的代价：* 回填正确性验证变弱一档（不再覆盖全表），但保留了对具体旧行的断言。

**Ruling B：导入的幂等判定要加内容比较。**
`KBPermission.updated_at` 是 `default=utcnow`，**没有 `onupdate`**——ORM 的 `setattr` 更新不会自动改
`updated_at`。所以第二次导入时 `updated_at` 仍等于插入时间（早于第一批的 `finished_at` 基线），
会走「更新」分支，得到 `updated: 2` 而不是计划里断言的 `updated: 0, skipped: 2`。
改为：**内容与库中完全一致时直接计为 skipped（no-op）**，只有内容确有差异才走
「是否被人工编辑」的判定。这样三条测试同时成立，且语义更准（没有变化就不叫更新）。
*若判断有误的代价：* 多一次字段逐一比较的开销（千级行，可忽略）。

**Ruling C：T8 必须同步修正既有测试。**
`test_permission_kb_api.py::test_meta_exposes_controlled_vocabulary` 断言 `len(permission_types) == 8`；
T8 之后不传 platform 时 meta 返回三平台并集，该断言失败。T8 计划里已提示要改，
此处明确为**必做项**（传 `platform=ANDROID` 再断言 8 个），并要确认 `test_update_rejects_invalid_permission_type`
仍成立（编辑态的校验用行自身的 platform，该行是 ANDROID，写「普通/受限 API权限」仍应被拒）。
*若判断有误的代价：* 无——不改就是回归红。

**Ruling D：导入对词表外的 `permission_type` 取「跳过并计数」，不中止。**
计划中 T6 的 `validate_permission_type` 会让**整批导入**因一行取值异常而抛错——1018 行的导入
死在最后一行是不可接受的。改为：导入时逐行校验，非法行**跳过并计数**、写进批次统计；
API 侧（T8）保持严格抛 400。相应地 `test_import_rejects_type_not_in_platform_vocabulary`
改为断言「该行未被写入且计入 skipped」，而不是断言抛异常。
理由：批量数据不该有能力污染受控词表，但也不该让一行脏数据毁掉整批——两种失效都要挡住。
*若判断有误的代价：* 脏数据会静默进不了库（有统计与日志留痕），需要看批次统计才能发现。

## Ruling H / I（Task 4 修复轮）

审查者指出鸿蒙解析器的正文**只被下一个 `## ohos.permission.X` 收口**，于是夹在中间的非权限 `##` 小节
会被吞进上一段；而级别是 `.search()` 在整段里找的——**一个自己没有「权限级别」的权限小节会继承邻居的
级别**（`capability` 还会一并吞掉那段说明文字）。这正是 spec 硬约束「宁可少收，不编造」要挡的形态，
`if not level_m: continue` 那道闸挡不住。

**Ruling H：正文一律被下一个 `##` 标题收口，不管它是不是权限标题**；顺带把 `desc` 的硬编码字面量
`split` 换成按级别正则的匹配位置切（文档若写 `**权限级别:**` 冒号在加粗内，字面量 split 会让
`capability` 变成整段）。已改计划并派修复轮。
*若判断有误的代价：* 正文收窄后若真实文档把级别字段写在下一个 `##` 之后，该条会被跳过少收——有 T7 的条数断言兜底。

**Ruling I：鸿蒙的 `official_reference` 一律置 `None`。** 原实现拼的
`https://developer.huawei.com/.../{name}` 是猜的、很可能 404，而**错误的官方链接比没有更误导**，
且与 spec 的「不得编造」相抵。溯源信息已在 `raw_data.platform_source='openharmony_docs'` 中。
*若判断有误的代价：* 少了一个直达链接，用户需自行去 OpenHarmony 文档检索。
