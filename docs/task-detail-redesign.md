# 任务详情页改造方案

页面：`/tasks/:id`（`frontend/src/views/TaskDetail.vue` + `components/ComplianceProfile.vue`）
样本：任务 2216 / 营行企业银行 1.4.2 / 静态检测 / 已完成
写于 2026-09-29。实测截图与接口数据均取自当日运行实例。

---

## 零、先说结论：丑不是配色问题

现有 token 体系（主蓝 `#2B5AED` + 灰阶 + 4/6/8px 圆角）是自洽的，**不推翻**。
为一个页面改全局品牌色是错的。真正的问题按严重度排：

1. **首屏主语错了** —— H1 是 `task_001a0eb1154ec670c002ab5e12649`，
   真正有意义的信息被降级成灰色小字副标题。审计人员第一眼看到一串机器 ID。
2. **信息架构失衡** —— 「合规画像」3275px，视口 1144px，要滚 2.9 屏且无锚点；
   「风险结论」只有 200px。tab 上无计数，不知道哪个 tab 有东西。
3. **表格里全是噪音** —— 见第四节，每条都有实测数字。
4. **色彩语义倒挂** —— 两个 0 值统计卡用了橙色（警告色）。0 是好事。
5. **口径自相矛盾** —— 同一屏上「第三方组件 3」与「已识别第三方组件 9」并排，
   数字不同却同词；「未识别三方包 0 处」与下方 9 行列表并排。
   *（第 5 条的根因是后端数据缺陷，已单独修复，见第七节）*

一句话：丑来自**层级缺失 + 密度失控 + 语义错位**，不来自颜色。

## 一、首屏：主语换掉

```
营行企业银行  1.4.2                              [生成检测报告 ▾]  [⋯]
task_001a0…e12649 ⧉ · 静态检测 · 09-29 02:56 完成      已完成 · 分析有效
```

- H1 ← App 名 + 版本；任务号降为等宽小字，可一键复制
- 3 个按钮收到 **1 个主 CTA + 溢出菜单**：
  - 「生成报告」是**动作**，占主位
  - 「检测报告」是**查看产物**，进溢出菜单
  - 两者同屏并排、语义撞车，是当前最容易点错的交互
- 删掉顶部「任务信息」折叠条：它展示的 App/类型/时间三个字段，副标题已经有了

## 二、统计条：从展示变成导航

5 个数字当前是死的。改成**可点击 → 滚动到对应区块并高亮**。

色彩语义修正（写死规则：**颜色只表达「需要注意」，不表达「有数据」**）：

| 卡片 | 现值（2216） | 当前 | 应为 |
|---|---|---|---|
| 个人信息采集点 | 16 | 主蓝 | 保持主蓝 |
| 涉及的第三方组件 | 3 | 中性 | 改为「涉及第三方**厂商**」 |
| 应用自身代码中的采集 | 0 | 深色左边框 | 中性灰 |
| 敏感个人信息类目 | 0 | 🔶 橙色 | 中性灰 |
| 申请权限 | 14 | 中性 | 保持 |

- 左侧色条目前是纯装饰（5 条彩条抢视线），**整个去掉**，改用数字/标签的字重对比建立层级
- **口径统一**：统计卡「第三方厂商 3」vs 下方「已识别组件 9」——
  一个数厂商、一个数组件，必须换词区分

## 三、长页：tab 内锚点目录

```
[合规画像] 风险结论 ②  执行信息 ③  证据 ⑥     ← tab 加计数徽标
──────────────────────────────┬───────────────
 一、个人信息收集               ┆ ▍个人信息收集
 二、权限使用                   ┆   权限使用
 三、第三方组件                 ┆   第三方组件
 四、数据缺口                   ┆   数据缺口
   (滚动跟随高亮)               ┆  ← 粘性目录
```

3275px 缩不下来，但可以让人**不用滚**。tab 徽标解决「哪个 tab 有东西」。

## 四、表格去噪

实测 2216 的数据（`/api/v1/tasks/2216/compliance-profile`）：

| 问题 | 实测 | 处理 |
|---|---|---|
| 「隐私政策」列 | **6/6 行**均为「无数据」（`declared_in_policy` 全为 `null`） | **整列删除**，改区块级一条说明 |
| 「无需权限」标签 | **6/6 行**重复（`requires_permission` 全 true） | 反转语义，只标「需权限」 |
| 权限「无法判定」 | **9/14 行**同一句「权限映射未覆盖」 | 折叠成一组 + 一条说明，默认只显示可判定的 5 行 |
| 「申请但未见使用 (0)」筛选 | 计数为 0，点了必然为空 | 计数为 0 时不渲染 |
| 归属列厂商名 | 换行 2–3 行把行撑高 | 厂商名降为 12px 次行，限宽不折 |

**通用规则：某列全部同值时，它不该占一列。**

## 六、视觉体系（已落地）

### 6.1 调色板

取自 skill `--domain color` 的 **Analytics Dashboard** 条目（深企业蓝 + 琥珀强调）。

**关键不是"换一个蓝"**，而是这两条——它们决定了页面看起来是"设计过的"还是
"默认组件拼的"：

| 项 | 旧 | 新 | 为什么 |
|---|---|---|---|
| 标题文字 | `#1F2329` 灰黑 | **`#1E3A8A` 蓝墨** | 整个页面的气质由它决定 |
| 边框 | `#E8EDF5` 中性灰 | **`#DBEAFE` 蓝调** | 中性灰边框是"默认组件"的味道 |
| 阴影 | 黑色投影 | 蓝调投影 | 中性灰阴影铺在蓝调界面上显脏 |

其余：主色 `#1E40AF`、次色 `#3B82F6`、强调 `#D97706`（琥珀）、
页面底 `#F8FAFC`、表头/悬停底 `#EFF6FF`。

**品牌主色 `--el-color-primary` 保持 `#2B5AED` 不动** —— 换它等于改整个产品的
识别，不是一次页面改造该做的决定。`#1E3A8A` 与 `#2B5AED` 同属一个色族，并存不冲突。

### 6.2 密度

取自 skill `--domain style` 的 **data-dense-dashboard**：
`--grid-gap: 8px` / `--card-pad: 12px` / `--table-row-height: 36px`。

### 6.3 字阶

```
H1 App 名        20px / 600 / -0.3px / 蓝墨
KPI 数字         28px / 600 / -0.5px / 主蓝
区块标题          14px / 600 / 蓝墨
表头、标签         12px / 500
正文             13px / 400 / 1.6
次要信息          12px / 400
数字             tabular-nums
```

### 6.4 色彩语义

**颜色只表达"需要注意"，不表达"有数据"。** 0 值一律中性灰；
需要提醒的项才上琥珀，且只用右上角一个小圆点强化，不整块变色。

### 6.5 字体：为什么没用 skill 推荐的 Fira

skill 的 `--domain typography` 对这类仪表盘推荐 Fira Code + Fira Sans，
`--domain color` 也重复了这条。**没有采用**，原因是部署形态：

本平台是**内网部署**（`172.16.105.2` / frp 隧道）。引 Google Fonts 等于给页面
加载引入外部网络依赖；用户浏览器一旦够不到，排版会静默退化到系统字体，
而且这种退化不报错、很难被发现。

另外 Fira Sans **不含中文字形**——中文会回退到 PingFang/雅黑，形成
"拉丁字母是 Fira、汉字是系统字体"的混排，未必比统一系统字体好看。

替代方案：系统字体栈 + 强化等宽栈（`ui-monospace` / JetBrains Mono / SF Mono /
Menlo / Consolas）。这个产品的拉丁内容密度很高（包名、SHA256、SDK 名），
等宽栈的收益最大、风险为零。

> 如果确认使用者浏览器可直连 `fonts.googleapis.com`，加一行 `@import` 即可启用
> Fira；改动点只有 `index.css` 一处。

### 6.6 落地范围

设计令牌与 Element Plus 主题变量是**全局**的（`index.css`），
但版式改造只应用到**任务详情页及其子组件**。
起因见下节。

### 关于「视觉体系重做」的落地范围

把字阶/间距做成 **`index.css` 里的全局语义 token**（`--text-*` / `--space-*`），
这样其他页面可以逐步迁移。但**本次只应用到任务详情页及其子组件**，
不一次性改动其余 20+ 页面 —— 那会让全站观感在迁移期不一致，
且 Element Plus 默认样式需要成批覆盖 CSS 变量才能生效。

## 七、配套的后端修复（已完成）

「未识别包簇」面板列出的包**根本不是包名**。全库 272 条包簇里 **190 条（70%）**：

```
android.permission                14 个「类」   ← 权限命名空间
ACCESS_FINE_LOCATION / CALL_PHONE / READ_EXTERNAL_STORAGE   ← 权限名
file://localhost/ , http://www.openssl.org/support/faq       ← URL
libjpeg.so → libjpeg                                          ← .so 文件名
<com.thirdparty.tracker: void send()> → <com.thirdparty.tracker  ← AppShark 残壳
```

根因在 `app/services/sdk_analysis.py`：聚类直接把事件 `api`/`caller` 当类名切分，
而这两列在不同事件类型下装的是权限、URL、.so 文件名、AppShark 签名。

**两道门**（均为默认拒绝，不做兜底猜测）：

1. **类型门** —— 只有候选串承载代码符号的事件类型才参与聚簇
   （`static_component` / `static_sensitive_api` / `static_data_flow` / `security_observation`）。
   权限、URL、`.so`、basic_info、tracker 全部挡在门外。
2. **形态门** —— 剥掉 AppShark 外壳后须是合法 FQCN，且不属于平台命名空间
   （`android.*` / `java.*` / `kotlin.*` …）。

剥壳逻辑收敛到 `component_matcher.strip_appshark_shell()` 一处：
匹配路径早已剥壳、聚类路径没有，两处口径不一致正是残壳的来源。
`normalize_candidate()` 在其上叠加小写化，外壳规则只有一份定义。

**为什么不挡平台命名空间不行**：剥壳后 `static_sensitive_api` 的候选变成合法 FQCN，
`android.content.pm` 会以 4647 条事件的体量成为最大的那个「包簇」——
把一个众所周知的东西列成「待分析」，比列不出来更误导。

结果：

| | 修复前 | 修复后 |
|---|---|---|
| 全库包簇 | 272 条，190 条非包名 | 146 条，**0 条非包名** |
| 任务 2216 | 9 条全是垃圾 | 0 条（该 App 调用点已全部归属） |
| 任务 2348 | 90 条中 83 条垃圾 | 8 条真实第三方包 |

副作用（正确的那种）：2216 的「暂时无法识别」面板变空了。
原先那 9 条是凭空的，现在页面也不再自相矛盾（统计卡说 0，面板就列 0）。

存量数据不会自愈 —— `analyze_task` 命中「已分析过」会提前返回，
所以修复后需对已有扫描记录强制 `refresh` 重算一次（已执行）。
